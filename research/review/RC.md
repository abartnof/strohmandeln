## 4. Judgement on the recommended git-submodule "card-table-kit" (note 10 §6.4, not rewritten)

Short verdict: the kit idea (extract what stayed identical) is well grounded in the repos' own stated policy; the submodule mechanism is the weakest part, and at least one claimed benefit is false as written.

1. **esbuild cannot resolve the game's libraries from inside the kit.** The note says esbuild "resolves `import ... from '../../kit/js/scene.js'` directly". It does, but `kit/js/scene.js` imports bare `three`, and bare specifiers resolve by walking up from the importing file: `kit/js/` -> `kit/` -> repo root, never `web3d/node_modules`. I reproduced this in a scratch directory with cassino's esbuild: `Could not resolve "three"` from `../kit/js/scene.js`. Fixable (`NODE_PATH`, `--alias:three=...`, or `nodePaths`/a root-level `node_modules`) but it needs a build.py change and a decision on where `npm ci` lives; the note presents it as free. The kit's own node tests (the note wants them in the kit) hit the same problem.
2. **Claude Code worktrees.** Cassino has 13 live `.claude/worktrees/agent-*` worktrees today (`git worktree list`) and merges from them often (many "Merge branch 'worktree-agent-...'" commits). `git worktree add` does not populate submodules, so each agent starts with an empty `kit/`; build.py, Cargo and the gate all fail until `git submodule update --init` is run per worktree (and with a local-path submodule URL, git >= 2.38.1 refuses the file transport unless `protocol.file.allow=always` is set). The existing setup already shows the same class of trouble: cassino's `.gitignore` carries the comment "an agent worktree once linked [node_modules]", and the gate silently *skips* the Node tests and page check when `web3d/node_modules` is absent, which is the wrong failure mode for a missing kit (it must fail loudly). An agent that edits the kit from inside a game worktree creates a commit in a detached submodule worktree and a pointer change in the superproject: two repos, two commits, and a pointer to a commit that was never pushed is a classic way to break the other worktrees. The "atomic commits, often" rule becomes two-repository atomic commits.
3. **GitHub Pages.** The note says Pages is unaffected because it serves the committed html. That is probably right for serving, but untested: the legacy branch deployment still checks the repo out, and a `.gitmodules` entry pointing at an unreachable (private, or ssh-form) URL can fail that checkout. Bezique is already private, so a private kit repo is plausible. Make the kit public, use an https URL, and test with a throwaway branch before relying on it. Also no GitHub Actions exist in the repos, so nothing but the local gate would ever check the pin; a bad pointer merged to `main` goes live.
4. **Cargo.** Not tested (no cargo in this shell). Known behaviour to check before committing: a path dependency that lives under the workspace root (`kit/rust/...`) is pulled into the game's workspace automatically; if the kit also has its own `[workspace]`, cargo reports multiple workspace roots unless the game excludes it. Separately, the kit's lockfile and the wasm32 target/toolchain pin (cassino pins 1.98.1, piquet 1.97, bezique 1.98) will conflict; one kit must pick a toolchain for all consumers.
5. **Keeping the three older games in sync.** The note says "no obligation ... they are finished". Cassino is not finished (293 commits, page rebuilt 13 Oct, untracked `check_*` dirs, 13 worktrees); it will keep improving the files the kit was cut from, so the kit forks from its source on day one, and the older games only benefit if someone back-ports. Of the 23 web3d file pairs, only 6 are identical (plus rng.rs on the Rust side); the rest are "take cassino's" or "rewrite per game", i.e. the kit would consist largely of files nobody has yet generalised (`faces.js` rank/suit sets, `units.js` zones, `engine.js` exports, `build.py` -> `game.toml`). Designing those abstractions from a single consumer that is itself still being designed (Strohmandeln: 54 cards, trumps with numerals, straw-man piles) risks a kit shaped like cassino. Keeping piquet and cassino on their own copies means the origin-header diff convention (`// From piquet ... @ sha`) still has to be maintained anyway, so the submodule does not remove the old mechanism, it adds a second.
6. **The repos' own trigger is unmet.** `cassino/docs/DESIGN.md` §3 defers a shared package "until the bezique and cassino tables both exist", and bezique's table is unchecked (`PLAN.md:202`). Note 10 states that bezique has no table, but not that this blocks the planned diff.

What I would weigh instead (judgement, not a rewrite): treat the fallback (vendored `web3d/kit/` with a stamp file and a `bin/sync-kit`, headers retained) as the default for the first game that consumes it, because it works in fresh worktrees, with bare imports (files sit under `web3d/`), with Pages, and with no cargo workspace puzzles; promote to a submodule or a real package only once a second consumer has needed a kit change, and make the gate fail (not skip) when the kit is absent or the stamp disagrees with the files. If a submodule is chosen anyway: public repo, https URL, esbuild `nodePaths` for the game's `node_modules`, `git submodule update --init` in CLAUDE.md and in whatever script creates worktrees, and a gate check that fails on a missing, dirty or unpushed pin.

## 6. Verdicts

- **06: usable with care.** Citations are largely real and the three particular worries check out: (a) *1824 Haas "Strohmandeln"*: true (page 109, preface Jan 1824) but only a bare name in a list; (b) *whist Strohmann 1839*: true (Bohemia no. 54, 5.5.1839, via metadata), and the 1841-1858 hits are genuine; the "no earlier" claim rests on one library and is properly caveated; (c) *de Gébelin 1781, 25-card mort*: Dummett says exactly "a dead hand of twenty-five cards" and dates the account 1781. Weaknesses: the "Viennese Taroc en deux of 1800" uncited claim (#2), the Werner last-card distortion (#3), the 1887 article over-read (#6), several ANNO inferences presented as readings (#10), and the Morto/Baronetti attributions (Morto correct; Baronetti pile count wrong, fixed). The "root is a dead hand" hunch is labelled a hunch, but note 01 argues the opposite about the 1805 text; the claim should not go into the final review unqualified.
- **10: usable with care, mostly accurate.** Of 48 sampled claims, 8 were wrong, all peripheral (primitive lists, scene count, file counts, OBF attribution), all fixed; the central claims (no shared crate, the planned diff, the exact quotes and their locations, the licences, the gate, the diff matrix, the Jumbo recipe) are correct. The recommendation in §6.4 needs the caveats in §4 above before anyone acts on it.
